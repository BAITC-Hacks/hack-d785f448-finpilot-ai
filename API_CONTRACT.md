# Фактический API локальной сборки

Источник: `serve.py` и `assistant.py` из опубликованного `main` (`1e56e56`) с интеграционным исправлением health. Базовый адрес `http://localhost:8000`, все вызовы браузера — на тот же origin. GID всегда строка.

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | Готовность приложения и PostgreSQL; `mode`, `model`, число узлов и счётчики шести таблиц |
| `GET /api/db/health` | Отдельное состояние БД |
| `GET /api/explain?gid=100000002398779100` | `{facts, answer}` — факты и объяснение |
| `GET /api/decide?k=3` | `{candidates, answer}` — выбор среди первых k |
| `GET /api/whatif?exclude=100000002398779100` | Пересчёт сценария прекращения передачи через выбранный узел |
| `GET /api/request?gid=100000002398779100` | `{status: "awaiting_human_approval", draft, note}` — черновик |
| `GET /api/request?gid=100000002398779100&confirm=1` | Существующий маршрут подтверждения: `{status: "saved", path, draft}` |

В опубликованной версии **нет** POST `/api/agent`, POST `/api/approve` и записи отклонения в БД. Это расхождение с ранее предложенным контрактом, а не реализованные возможности. Текущий фронт вызывает перечисленные GET-маршруты. Для нового контракта нужен согласованный переход фронта и серверного адаптера; `web/` интегратором не редактируется.

## Формат объяснения

```json
{
  "facts": {
    "gid": "100000002398779100",
    "role": "consolidator",
    "seed_reach": 8,
    "in_deg": 13,
    "out_deg": 1
  },
  "answer": {
    "summary": "Текст объяснения",
    "hypotheses": [],
    "alternative_explanations": [],
    "missing_data": [],
    "next_step": "check_neighbors",
    "next_step_reason": "Основание следующего шага",
    "_source": "template"
  }
}
```

Пример показывает основные поля, не полный объект `facts`. `seed_reach` — число других seed с направленным путём **seed → … → выбранный клиент**, без ограничения длины пути; обратное направление метрика не описывает. `top_in[].from` — плательщик, `top_out[].to` — получатель. Роли являются гипотезами, `seed_money` — результат модели смешивания.

`next_step`: `check_neighbors`, `request_data`, `mark_legit`, `escalate`, `none`.

## Режим и ошибки

- Без `OPENAI_API_KEY`: health сообщает `mode: "replay"`, `model: null`. `_source: "replay"` означает сохранённый ответ, `_source: "template"` — шаблон из фактов. Шаблон не является вызовом LLM.
- С ключом: `mode: "live"`, модель задаётся `OPENAI_MODEL`; ответ содержит `_source: "live:<model>"`. При ошибке модели текущий код возвращает шаблон с пометкой ошибки в `_source`. Такой ответ нельзя засчитывать как успешный live-тест.
- Некорректный GID/параметр: HTTP 400 и `{"error": "..."}`.
- Неизвестный путь: HTTP 404; в текущей реализации тело может быть HTML.
- `/api/health`: HTTP 503 и `ok: false`, если настроенная PostgreSQL недоступна. Без настроенной БД локальный режим может возвращать `ok: true` и `db.configured: false`; для приёмки Compose требуется также `db.ok: true`.

## Открытые дефекты для проверки

Текущий журнал подавляет ошибки записи PostgreSQL. Повторный `confirm=1` повторно пишет подтверждение, а отклонение обрабатывается только в интерфейсе. Эти операции требуют доработки; успешный HTTP-ответ исходной версии сам по себе не доказывает запись в базе.
